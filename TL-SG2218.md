# TL-SG2218 — SNMP/LLDP status

Investigated 2026-09-02 against `SNMP_DEVICE_SETUP.md`'s Scanopy requirements.
Device: TP-Link TL-SG2218, `10.10.10.2`, SSH `tech@` (see
`SNMP_HOSTS.md`/`SNMP_HOSTS_CREDS.md`). TP-Link markets this model as a
JetStream/Omada Smart Switch (not "Easy Smart" as an earlier draft of this
doc said).

- Hardware: `TL-SG2218 1.0`. Software: `1.1.8 Build 20230602 Rel.73473`.
  Bootloader `TP-LINK BOOTUTIL(v1.0.0)`. Serial `2214067000962`. (`show
  system-info`, 2026-09-02.)
- Boot: single active image (`image1.bin`, flash `1.3.0`, software `1.1.8`)
  plus a backup image (`image2.bin`, software `1.1.7`). `firmware upgrade`
  (TFTP) is the only firmware subcommand this build exposes.

## Access

- SSH: `ssh tl-sg2218` authenticates fine, but only over an interactive pty —
  the switch's CLI rejects a plain exec channel and a shell channel without
  `pty-req`. Needs a real terminal (PuTTY, Windows Terminal, etc.); doesn't
  work from a piped/non-interactive session.
- CLI mode: connects in user EXEC mode. Run `enable` first before `show ...`
  commands work (no password prompted for this account in this session).
- SNMP: v2c, two read-only communities configured, both view `viewDefault`
  (`show snmp community`):
  - The community Scanopy's `TPLinkSNMP` credential uses (plaintext value in
    the gitignored `SNMP_HOSTS_CREDS.md`, not repeated here).
  - `homelab` — unused by Scanopy as far as we know; not investigated further.
  - `viewDefault` includes the entire `.1` tree, excluding only
    `.1.3.6.1.6.3.{15,16,18}` (standard SNMP-security subtrees, not
    device-specific). Confirmed via `show snmp view`. So the read-only
    community is **not** access-restricted — anything that fails isn't a
    permissions/view problem.
  - Also present but unused by Scanopy: an SNMPv3 user `scanopy` (`smode v3
    slev authPriv`, auth SHA / priv DES, group read view also `viewDefault`)
    — visible only in `show running-config`, not in `show snmp
    community`/`show snmp view`. Same access level as the v2c community
    either way; noted here in case it's a leftover from an earlier setup
    attempt.
- **`access-list 900`, bound to all 18 ports, restricts inbound UDP/161 to
  source `10.10.10.4` only** (Scanopy's daemon) — every other source is
  silently dropped, at the IP/port level, before SNMP even sees the
  request. This is deliberate hardening, not a bug, but it's a trap for
  manual testing: **any `snmpwalk`/`snmpget` run from a machine other than
  `10.10.10.4` will time out regardless of community or OID**, and looks
  identical to "the switch doesn't implement this MIB." Always test from
  `10.10.10.4` (or the corresponding logic that runs there) to get a real
  answer. (This bit us once already — see "Confirmed working" below.)

## Confirmed working over SNMP

- `sysDescr`/`sysName`/`sysObjectID` (SNMPv2-MIB) — Scanopy already polls
  this.
- `ifTable`/`ifXTable` (IF-MIB) — 19 interfaces polled per
  `SNMP_HOSTS_CREDS.md`.
- `LLDP-MIB` chassis id + `lldpRemTable` (remote neighbours) — this is how
  krusty (ports `Gi1/0/3-6`) and ralph (`Gi1/0/15`) currently resolve as
  neighbours in Scanopy (confirmed live via `/api/v1/if-entries` on
  2026-09-02, after the krusty/ralph SNMP credential fixes).
- **TP-Link's private FDB MIB — `tpl2BridgeManageDynAddrCtrlTable`,
  `.1.3.6.1.4.1.11863.6.10.1.2.2` (`docs/privateMibs/tplink-l2Bridge.mib`).**
  An initial `snmpwalk`/`snmpget` against this OID from a non-`10.10.10.4`
  source timed out and was wrongly logged below as "not implemented" —
  re-running the identical commands **from `10.10.10.4`** (the address
  `access-list 900` actually permits) succeeds, verified 2026-09-02 via a
  full walk run as `osit@10.10.10.4`. Since that's Scanopy's own daemon
  address, this MAC-table data is genuinely reachable today; Scanopy just
  doesn't collect it yet. All 24 rows matched `show mac address-table`
  exactly — e.g. row index `...1.1.160.54.159.168.137.238.1` (MAC bytes
  `160.54.159.168.137.238` = `a0:36:9f:a8:89:ee`, krusty) → column `.1`
  (`tpl2BridgeManageDynMac`) `"a0-36-9f-a8-89-ee"`, column `.2`
  (`tpl2BridgeManageDynVlanId`) `1`, column `.3`
  (`tpl2BridgeManageDynPort`) `"1/0/3"`. This is the one actionable finding
  in this doc — see "Next step" below.
  - **Implementation note:** the row index is the MAC's 6 bytes in decimal
    (not the usual hex-colon form) followed by the VLAN id, matching the
    MIB's `INDEX { tpl2BridgeManageDynMac, tpl2BridgeManageDynVlanId }`.
    The port column (`.3`) is a formatted string like `"1/0/6"`, **not** a
    numeric ifIndex or bridge-port number — a collector needs to match it
    against `ifDescr` (`"gigabitEthernet 1/0/6"`) rather than treat it as
    an index to look up directly.
- TP-Link's private VLAN MIB (`vlanConfigTable`/`vlanPortConfigTable`,
  `.1.3.6.1.4.1.11863.6.14.1.{1,2}...`) — same correction, also confirmed
  reachable from `10.10.10.4`. `vlanConfigTable`'s description column
  returned exactly one row (`VLAN 1` → `"System-VLAN"`), and
  `vlanPortConfigTable`'s PVID column returned 18 rows, all PVID `1`,
  indexed by `ifIndex` values `49153`-`49170` (TP-Link's internal ifIndex
  numbering for this switch's 18 physical ports, one per port in order —
  worth confirming against this switch's own `ifIndex` values from the
  standard `ifTable` walk before relying on that offset elsewhere). Low
  practical value here regardless, since there's only the one VLAN.

## Confirmed working over native CLI (not exposed via SNMP — see below)

Run 2026-09-02 by the user directly (`enable` then):

- `show mac address-table` — 24 dynamic entries, MAC↔VLAN↔port, e.g.
  `a0:36:9f:a8:89:ee` on `Gi1/0/3` (krusty), `4e:8e:7d:9d:d0:a2` on `Gi1/0/5`
  (ralph). This is the FDB the standard BRIDGE-MIB would normally expose.
- `show vlan` — single VLAN, `1` (`System-VLAN`), all 18 ports members. No
  real VLAN segmentation on this switch today.
- `show lldp` — LLDP enabled, standard timers, nothing unusual.

## Confirmed NOT working over SNMP

From the 2026-09-01 discovery run's warnings for `10.10.10.2` — these came
from Scanopy's own daemon (`10.10.10.4`), so unlike the private-MIB false
negative above, `access-list 900` does **not** explain these; the daemon is
the one source it permits. These are genuine gaps in this firmware:

| Group / OID | Result | Notes |
|---|---|---|
| `BridgePortNumbering` (`dot1dBaseNumPorts`, BRIDGE-MIB `.1.3.6.1.2.1.17`) | `SnmpWalkBridgeMibAbsent` | Standard BRIDGE-MIB not implemented. |
| `VlanNames` (Q-BRIDGE `dot1qVlanStaticName`) | `SnmpWalkNoAnswer` | Standard VLAN-MIB not implemented. |
| `ArpTable` (`ipNetToMediaTable`) | `SnmpWalkNoAnswer` | |
| `DeviceInventory` | `SnmpWalkNoAnswer` | |
| `IpAddresses` | `SnmpWalkNoAnswer` | |
| `LldpLocalPorts` (`lldpLocPortTable`) | `SnmpWalkNoAnswer` | Local-port table missing even though remote-neighbour table (`lldpRemTable`) works fine. |
| `Cdp` (Cisco CDP-MIB, `.1.3.6.1.4.1.9...`) | `SnmpWalkNoAnswer` | A TP-Link switch was never going to implement Cisco's proprietary MIB — kept as a control case: it times out identically to the rows above, confirming that (from a permitted source) a timeout here really does mean "not implemented." |

**Conclusion:** standard BRIDGE-MIB, Q-BRIDGE/VLAN-MIB, and the ARP/CDP/
LLDP-local-port tables are genuinely absent from this firmware
(`1.1.8 Build 20230602 Rel.73473`) — confirmed from the one source
(`10.10.10.4`) that isn't affected by `access-list 900`. But TP-Link's own
private FDB MIB **is** implemented and reachable from that same source (see
above), which means MAC-table-based placement for non-LLDP devices (the
printer, wireless clients behind the AX11000) is achievable here after all
— just not through the standard MIB Scanopy currently looks for.

One unverified lead surfaced during research (from an AI research report
synthesizing TP-Link's public docs, not independently confirmed by us): TP-Link
may have shipped a later firmware for the SG2218 line that fixes BRIDGE-MIB/
Q-BRIDGE-MIB compliance. This switch's hardware (`TL-SG2218 1.0`) is
reportedly upgradable to a `1.20.0` release, but whether *that* release (or
anything reachable from this hardware's upgrade path) actually contains the
BRIDGE-MIB fix is unconfirmed — the fix mentioned in that research was
attributed to a `1.30.6` release for different-numbered hardware (`1.30`/
`1.36`). Don't treat this as a firmware-upgrade recommendation; it would need
verification directly against TP-Link's official download page for this
exact hardware version before being worth the risk of an upgrade.

## Done — TP-Link private-MIB fallback for the bridge FDB

**Implemented 2026-09-02** in `backend/src/daemon/discovery/integration/snmp/`:

- `oids.rs`: `bridge::tplink_private::fdb_entry::TPLINK_DYN_FDB_PORT` —
  `.1.3.6.1.4.1.11863.6.10.1.2.2.1.3`.
- `values.rs`: `tplink_private_fdb_index_to_mac` — the table's `INDEX` carries
  the MAC and VLAN id, so only the port column needs walking.
- `queries.rs`: `query_bridge_fdb` now falls back to
  `query_tplink_private_fdb` whenever the standard `dot1dTpFdbTable`/
  `dot1qTpFdbTable` walk returns zero entries **and** `sysObjectID` is under
  TP-Link's enterprise OID (`is_tplink`). Ports come back as a display
  string (`"1/0/6"`), resolved against `ifDescr` by `tplink_port_to_if_index`
  rather than through `dot1dBasePortIfIndex` like the standard tables.
  Gated on the walk finding nothing at all, not on an explicit
  `noSuchObject`/`endOfMibView` response — a `GETNEXT` past an unregistered
  subtree is standard SNMP behaviour and not a reliably distinguishable
  signal, so requiring it would have missed exactly the case this exists
  for. Follows the same "vendor-quirk fallback" shape already established
  for Aruba/HP's `dot1qTpFdbTable`-only switches (GH #649).
- Regression test: `sim/devices/switch_tplink_easy_01.rs` — a device
  modelling the field-confirmed shape (no standard bridge/Q-BRIDGE-MIB at
  all, only the private FDB answers), covering both a resolvable port
  string and one naming a port the fixture's `ifTable` doesn't have (must
  come back `if_index: None`, not a wrong guess, and the row must still
  survive). Needed two additions to the sim framework along the way:
  `SystemInfo` (`sysDescr`/`sysObjectID`/etc.) wasn't served over the
  simulated wire at all before this — every device's `sys_object_id` sat
  unused in the fixture — and the private FDB needed its own file/
  registration rather than sharing the standard `bridge` one, since
  `bridge::BRIDGE_MIB` gets registered whenever any bridge file exists,
  which would make a "no standard BRIDGE-MIB at all" device leak its
  private rows into the standard-table walk.
- All three regression tests pass; full `cargo test --lib --features
  snmp-sim` run clean (1176 passed; the only failures are pre-existing
  Docker/testcontainers DB tests, unrelated — Docker isn't available in
  this environment). `cargo clippy --lib --features snmp-sim -- -D
  warnings` clean.

Not yet deployed/verified against the live TL-SG2218 through an actual
Scanopy discovery run — that requires shipping this backend change and
re-running discovery against `10.10.10.2`.

## What "should" be working — recheck list

Re-test these if the switch gets a firmware update, gets swapped for a
higher-tier model, or just periodically to catch drift:

1. **Switch port `Gi1/0/1` (OPNsense link).** `SNMP_DEVICE_SETUP.md`
   (written earlier, before this session) says OPNsense's LLDP neighbour on
   `igc1` already resolves to switch port `1/0/1`. A fresh
   `/api/v1/if-entries` check on 2026-09-02 (after the krusty/ralph fix)
   showed `gigabitEthernet 1/0/1` with `neighbor=null` on this switch's host
   record. Not confirmed as a regression — might just be this run's scope —
   but worth a manual recheck:
   ```
   curl -s -H "Authorization: Bearer $SCANOPY_API_KEY" \
     "http://$SCANOPY_HOST_IP:60072/api/v1/if-entries?network_id=cfe19907-3c72-48b1-a82a-75a9119cd1e1&limit=2000" \
     | jq -r '.data[] | select(.if_descr=="gigabitEthernet 1/0/1") | "\(.host_id) neighbor=\(.neighbor // "null")"'
   ```
2. **Switch ports `Gi1/0/10`/`Gi1/0/11` (MAXPOWER/HOMER).** Expected to stay
   unresolved until the Windows LLDP-resolver fork change lands (Scanopy
   currently can't match Windows' bare-hostname LLDP advertisement). Not a
   TL-SG2218 problem — recheck once that fork change ships.
3. **`show snmp community` / `show snmp view` drift.** If a firmware update
   or config change narrows `viewDefault` or adds a new community, standard
   polling (interfaces, LLDP) could regress. Re-run both commands after any
   switch firmware upgrade.
